# Running Buzz at System 2

*This is a fork of [block/buzz](https://github.com/block/buzz), tracking upstream on the
`s2` branch. **It used to carry no code changes. It now does** — session resume, the
s2harness system prompt, two transcript fixes, an observer frame-size ceiling and an
overridable dev port, each with its rationale and its upstream-merge check in
[`S2-CHANGES.md`](S2-CHANGES.md). That file is the one to read before merging a newer
Buzz, and the watch list in it exists so we drop our version the moment upstream has
one. Every change was a decision rather than a habit; keep it that way.*

Buzz hosts humans and agents in one set of channels. We join it as an ACP agent — our
harness ([system2tech/agent-harness](https://github.com/system2tech/agent-harness), branch
the ACP server) is generic, and Buzz is one of several clients that can spawn
it. That is why the setup lives here rather than there: the agent knows nothing about
Buzz.

Two facts shape everything below. **We need no fork:** our agent joins through a custom
harness registered in the app, and every adjustment is configuration. And **Buzz keys its
tenants on the literal Host header string**, which is the source of nearly every failure
worth documenting here.

## Setting it up

**Setup instructions live in [`.github/README.md`](.github/README.md)** — two paths, a
local relay or the team one, with the harness registration and the traps. This file
covers the model underneath: tenancy, relay schemes, and how to diagnose a silent
agent.

There used to be a `scripts/s2-setup.sh` that built Buzz and registered the runtime in
one step. It is deleted: it went stale faster than the four fields it was automating,
and a setup script that is wrong is worse than a table you can read. Registration is
four fields in the app.

## Joining as an agent

Buzz spawns an ACP-speaking binary and talks to it over stdio. `s2harness acp` is that
binary, so registration is a form, not a patch: **Settings → Agents → Agent
runtimes → Add runtimes → Custom harness** (fields in
[`.github/README.md`](.github/README.md)).

| field | value |
|---|---|
| Name / ID | `s2harness` |
| Command | `<repo>/.venv/bin/s2harness` |
| Arguments | `acp`, `--traces`, `<repo>/datasets/traces-acp` |
| Env | `AHA_PROFILE=<profile>` |
| Docs URL | `https://github.com/system2tech/agent-harness` |

`acp` deliberately has **no `--profile` default** — `cli.py` explains why: `buzz-acp`
splits `--agent-args` on commas without `allow_hyphen_values`, so a client cannot pass
`--profile x` through at all. `$AHA_PROFILE` is the only channel, and it falls back to
`deepinfra-smoke`. Set it explicitly; a mislabelled agent is otherwise invisible — an
agent named `s2-qwen3.8-27b` ran Kimi on DeepInfra for a day because the harness env said
so and the name did not.

The running profile is visible in the agent's log
(`~/Library/Application Support/xyz.block.buzz.app.dev.<slug>/agents/logs/*.log`) as
`profile=<name>`. Trust that over the name.

## Reaching it from a phone, with the relay on a laptop

The goal: be away from the Mac and still have agents working on it. Tailscale carries the
phone; the relay stays local. **This works**, and four things are required — each of which
looked like a different problem first.

### 1. `BUZZ_BUILD_AUTO_CONNECT_DEFAULT_RELAY=1`

Both onboarding branches — *Create a community* and *I own the community* — open
**Builderlab**, Block's hosted relay service. Hosted is the intended path for a new
community; there is no local-relay screen. This flag is the way out:

```rust
// desktop/src-tauri/src/commands/identity.rs
pub fn auto_connect_default_relay_enabled() -> bool {
    option_env!("BUZZ_DESKTOP_BUILD_AUTO_CONNECT_DEFAULT_RELAY").is_some()
}
```

`option_env!` — **compile-time**. No `.env` entry, exported variable, or restart reaches
it; the desktop must be rebuilt with it set. This is the single unlock, and the reason
config-only attempts fail no matter how correct they look.

### 2. `tailscale serve --tls-terminated-tcp`, not the HTTP proxy

`tailscale serve --https=443 http://127.0.0.1:3000` returns **`HTTP/2 502`** on the
WebSocket handshake. Not auth: `serve` negotiates h2, WebSocket needs an HTTP/1.1
`Upgrade`, and WS-over-h2 (RFC 8441) is implemented by neither end. Plain `GET` succeeds,
which makes it read like a permissions problem.

```bash
tailscale serve --bg --tls-terminated-tcp=443 tcp://127.0.0.1:3000
```

TLS terminates at Tailscale and raw TCP reaches the relay, so the upgrade survives. A
host-rewrite proxy in front of the relay is not needed and will keep dying if used.

### 3. `BUZZ_PAIRING_RELAY_URL`

The pairing QR embeds a relay URL, and without this it embeds `ws://localhost:3000` —
unreachable from a phone. `config.rs` has a field for exactly this, surfaced through
NIP-11:

```
RELAY_URL=wss://<host>              # the relay's own identity → NIP-42/NIP-98 scheme
BUZZ_RELAY_URL=wss://<host>         # desktop + agents
BUZZ_RELAY_HTTP=https://<host>
BUZZ_PAIRING_RELAY_URL=wss://<host> # what the QR carries
```

### 4. A fresh identity, in an isolated instance

**The relay URL of the community you joined is pinned in the macOS keychain.** It survives
deleting the whole app-state directory — you stay signed in and keep hitting the old host.
The symptom is a NIP-98 error naming a scheme you did not configure:

```
URL mismatch: event has `http://localhost:3000/query`,
              expected `https://localhost:3000/query`
```

Host `localhost:3000`, only the scheme moved: the relay's expectation changed, the app's
target did not. So an existing identity cannot be migrated by configuration.

A **git worktree** solves this cleanly, because Buzz derives per-instance identity from the
branch slug:

```
identifier:       xyz.block.buzz.app.dev.${BUZZ_INSTANCE_SLUG}
keyring service:  buzz-desktop-dev.${BUZZ_INSTANCE_SLUG}
```

Separate app-state directory, separate keychain entry, separate Vite port — a fresh
identity with nothing pinned, and the original checkout untouched.

```bash
git worktree add -b mobile-tailnet ../buzz-mobile
```

Only one relay can hold port 3000, so instances take turns; switching is which directory
you run `just dev` from.

## Why the relay scheme is global, and what it costs

`nip42_expected_relay_url` takes the **scheme from global config** and the **host from the
connection**:

```rust
let scheme = if config_relay_url.starts_with("wss://") { "wss" } else { "ws" };
format!("{scheme}://{}", tenant.host())
```

One relay therefore serves `ws` clients **or** `wss` clients, never both. An App Store
phone is forced onto `wss` by App Transport Security, so the relay must be `wss`, so
**every** client must be — including the desktop, which then depends on Tailscale being
up. That is the real price of the local route, and the reason a hosted relay on one real
domain is the cleaner end state.

## Host-keyed tenancy: the trap to know about

`scripts/seed-local-community.sh` creates **one community per spelling of the local host**
on every `just dev`:

```
localhost:3000    localhost    127.0.0.1    127.0.0.1:3000
```

They are four separate tenants. An agent in one sees nothing in another, logs
`discovered 0 channel(s) — sit idle`, and reports itself **online** with a green dot in the
UI. Nothing errors, because both tenants exist.

Consequences, all of them observed:

- The CLI defaults to `localhost:3000`. Point it at whatever the app uses, or it writes
  into a tenant nobody reads: `BUZZ_RELAY_URL=http://<app-host> buzz …`
- `channels.community_id` is **immutable** (a database trigger). To move a workspace
  between tenants, rename the community's `host` — the data cannot be re-tenanted.
- Onboarding will silently pick a spelling. Check which tenant holds your channels before
  concluding an agent is broken:

```sql
select c.host, count(distinct ch.id)
from communities c left join channels ch on ch.community_id = c.id
group by c.host order by 2 desc;
```

## Operational notes

**Claude Code runs on a subscription, not API credits.** Buzz's README says to export
`ANTHROPIC_API_KEY` for `claude-agent-acp`; that is unnecessary. Verified with
`ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and `ANTHROPIC_BASE_URL` all scrubbed —
`initialize` offered no auth methods and the agent answered. Setting the key moves you onto
API billing for no benefit. `codex-acp` does fall back to `OPENAI_API_KEY`, so the OpenAI
side is not cost-equivalent.

**Parallelism defaults to 10.** Each agent spawns up to ten runtime subprocesses. Three
built-in agents produced 32 live `claude-agent-acp` processes. Set it to 1 unless you want
the fan-out.

**Agents are added to channels as `role=bot` by default**, and `--respond-to` defaults to
`owner-only` — which drops *everything* when no owner is resolved. Both fail silently.

**Channel discovery runs once, at startup.** Adding an agent to a channel afterwards does
nothing until its harness restarts, despite the log line claiming a membership
subscription.

**Pin a commit.** Between `0e69b3f` and `c856be0fb` — days apart — the onboarding flow lost
its relay-URL entry screen, which is how a working local setup becomes a Builderlab prompt
with no code change on our side.

## Diagnosing a silent agent

In order, because each rules out the layer below:

1. `profile=` in the agent's log — is it the model you meant?
2. `discovered N channel(s)` — `0` means wrong tenant, not a stuck model
3. `relay=ws://…` in the same log — does the host match the app's?
4. Compare tenants with the SQL above
5. `NIP-42 auth successful` in the relay log — absent means scheme or host mismatch
6. Only then suspect the model

Steps 2 and 3 catch most of it, and neither is visible in the UI. A green dot means the
process is alive, not that the agent can do anything.

## What the UI does show, and why

Once an agent *is* correctly wired, its reasoning, tool calls and results appear in the
channel as it works — the "is it thinking or is it stuck?" question
`docs/status.md` in agent-harness raises answers itself in the normal case.

That comes from ACP, not from Buzz's UI being clever. The protocol carries typed
`session_update` notifications, so the client renders structured events instead of parsing
someone's stdout. It is the return on writing an ACP server: a workspace that has never
heard of us can show our agent's work correctly, with no adapter and no agreement about
log formats.

The gap is narrower than "we cannot see what agents are doing", and worth stating
precisely: **a working agent is legible; a misconfigured one is not.** The failures above
are all pre-flight — wrong tenant, gate closed, discovery missed — and they present as an
online agent doing nothing rather than as an error.
